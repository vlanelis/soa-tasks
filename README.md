# soa-marketplace

## 1. Домены маркетплейса

### 1.1 Identity & Access

**Ответственность:**
- регистрация пользователей
- аутентификация
- авторизация

---

### 1.2 Catalog

**Ответственность:**
- управление товарами
- категории
- атрибуты
- изображения
- доступность товаров

---

### 1.3 Personalization

**Ответственность:**
- формирование персонализированной ленты
- хранение пользовательских предпочтений
- сбор событий (просмотры, клики)
- логика рекомендаций

---

### 1.4 Order Management

**Ответственность:**
- оформление заказа
- управление статусами
- хранение истории заказов

---

### 1.5 Payment

**Ответственность:**
- расчёт стоимости
- фиксация транзакций
- интеграция с внешними платёжными провайдерами

---

### 1.6 Notification

**Ответственность:**
- отправка email / push
- уведомления о статусах заказов
- обработка событий системы

---

# 2. Вариант архитектуры 1 — Монолит

## Архитектурная модель

Все домены реализованы в одном приложении и используют одну общую базу данных.

### Характеристики

- единая кодовая база
- единый деплой
- общая БД
- логическое разделение модулей

---

## Границы владения данными

- одна физическая база данных
- таблицы логически разделены по доменам
- отсутствует техническая изоляция данных

---

## Плюсы

- простота реализации
- минимальная инфраструктура
- низкая операционная сложность

---

## Минусы

- отсутствие независимого масштабирования
- рост связности
- усложнение поддержки со временем

---

# 3. Вариант архитектуры 2 — Микросервисы

## Архитектурная модель

Каждый домен выделен в отдельный сервис.
Каждый сервис владеет своей базой данных.

Взаимодействие:
- синхронное — REST через API Gateway
- асинхронное — через Event Bus

---

## Распределение доменов по сервисам

| Сервис | Домены |
|--------|--------|
| Identity Service | Identity & Access |
| Catalog Service | Catalog |
| Personalization Service | Personalization |
| Order Service | Order Management |
| Payment Service | Payment |
| Notification Service | Notification |

---

## Границы владения данными

Каждый сервис:

- владеет своей базой данных
- не предоставляет прямого доступа к данным другим сервисам
- взаимодействует только через API или события

---

## Взаимодействия сервисов

### Синхронные

- Клиент → API Gateway
- API Gateway → сервисы
- Order Service → Payment Service
- Personalization Service → Catalog Service

### Асинхронные

- OrderCreated
- PaymentCompleted
- OrderStatusChanged
- UserActivity events

Через Event Bus.

---

# 4. Trade-offs

## Монолит

### Плюсы
- минимальная сложность
- быстрая разработка
- простота отладки
- низкие инфраструктурные затраты

### Минусы
- сложное масштабирование
- отсутствие изоляции отказов
- сложная поддержка при росте системы

---

## Микросервисы

### Плюсы
- чёткие границы ответственности
- независимое масштабирование
- изоляция отказов
- технологическая независимость

### Минусы
- высокая инфраструктурная сложность
- распределённые транзакции
- eventual consistency

---

# 5. Обоснование финального выбора

Выбран вариант: **Микросервисная архитектура**

## Причины выбора

1. Маркетплейс — потенциально высоконагруженная система.
2. Персонализация требует отдельного вычислительного контура.
3. Платежи требуют изоляции и повышенной безопасности.
4. Необходимо независимое масштабирование каталога и заказов.
5. Асинхронная модель хорошо подходит для обработки заказов и уведомлений.

Монолит допустим для MVP, но для production-системы маркетплейса микросервисная архитектура более устойчива и масштабируема.

# 6. Инструкция по запуску проекта

## Предварительные требования
- Установленный Docker и Docker Compose
- Git

## Запуск сервиса

### 1. Клонирование репозитория

```bash
git clone https://github.com/vlanelis/soa-marketplace.git
cd soa-marketplace
```

### 2. Запуск через Docker Compose

```bash
docker compose up --build
```
